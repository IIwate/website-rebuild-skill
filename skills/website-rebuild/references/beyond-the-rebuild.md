# 基于复刻产物继续开发

本 skill 的交付范围到用户选择的镜像、工程恢复或可读源码为止. 将其改为新的产品需要新的功能目标与相应资产使用条件. 本文件用于交接, 不自动创建目录、仓库或功能.

## 1. 保留可复核基线

`mirror/` 保存采集原件, `port/` 保存已验收移植, `src/` 是可读源码. 后续开发应保留一个可恢复的基线, 具体采用现有版本控制或用户已选择的目录方式. 不为此自动创建副本或工作树.

新需求可以改变命名、结构与行为, 但应区分已确认的来源事实、对原实现的推断和新产品的设计决定.

## 2. 用比较结果记录影响

`make-standalone.mjs` 生成的交付物可带 `byte-manifest.json` 和 `verify-bytes.mjs`; 拼接式产物可使用 `verify-reassembly.mjs`. 先检查实际交付物包含哪些工具, 不假定所有 `src/` 都有相同文件.

字节变化用于定位受影响文件, 不直接说明功能是否正确. 根据新目标更新对应验收条件, 对仍要求保持行为的部分复用现有检查. 有意改变的功能不应长期保留必然失败且无人处理的旧断言. 近似实现漂移的实例见 [case-studies/beyond-the-rebuild.md](case-studies/beyond-the-rebuild.md) §2.

## 3. 资产与代码许可

代码改动幅度不能作为是否取得使用权的判据. 检查保留的源站代码、图片、字体、媒体、文案与第三方库的实际许可证. 更换品牌或重写代码不自动改变其他资产的许可.

现有部署文档中的来源表可作为清单, 但应按新用途更新. 第三方库许可与版本相关, 包括 GSAP 等许可可能变化的组件, 不能用历史项目的条款替代当前适用许可证. 详见 `legal-and-deploy.md`.
