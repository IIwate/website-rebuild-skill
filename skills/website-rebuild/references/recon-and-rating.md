# 架构调查与工作量评估

用于确定目标行为、实现来源、数据依赖和验证方式. 依赖名与页面观感用于提出假设, 具体判断需要调用点和运行证据. 案例见 [case-studies/recon-and-rating.md](case-studies/recon-and-rating.md).

## 0. 调查结果

记录架构结论、恢复范围、尚未确认的依赖和主要工作量来源. 已有项目文档可直接承载这些信息, 不要求固定数量的新文件.

区分三类依据: 采集代码与数据描述实现, 目标版本的运行记录描述可观察结果, 本地镜像提供可重复基线. 本地适配属于实验条件, 不能当作原站需求. 若线上版本已变化, 不用它覆盖历史基线.

## 1. 验证架构假设

确认视觉主体由 WebGL、Canvas 2D、DOM/CSS 或平台运行时的哪一层实现. 对每个疑点查找支持和反例, 包括能力是否仅存在于 vendor、是否实际挂载、是否只在特定状态触发.

记录假设、源码位置、观察结果与结论. 未确认项保留其不确定性, 只暂停依赖它的实现, 不阻止其他已确定工作.

## 2. 字符串与版本线索

源码检索用于缩小范围. 命中可能来自库内部或相似子串, 未命中也可能因混淆、内联或动态拼接. 版本字符串、pnpm 路径、WASM URL 与 API 特征提供不同强度的证据; 只有足够明确时才给出精确版本.

noomo 从 `179` 等值确认 three 版本, oryzo 使用 `#define GLSLIFY 1` 定位 shader, samsy 将 `dispatchWorkgroups` 命中归属到 vendor. 对应上下文见案例 §2. 临时换行视图只用于检索, 不作为行号或代码基准.

## 3. 工作量与风险

按与目标相关的维度评估, 使用低/中/高或明确数量, 每项给出依据与不确定性. 等级是规划辅助, 不是验收条件.

| 维度 | 影响工作量的因素 | 参考 |
|---|---|---|
| 资源获取 | 体积、跨域条件、运行时拼接、查询变体 | `mirroring.md` |
| 渲染 | 场景数、shader、后处理、DOM 几何依赖 | `webgl-scenes.md` |
| 动画与输入 | 代码或数据来源、状态数量、生命周期 | `animation-recovery.md` |
| 二进制数据 | 格式、解码器、WASM、worker 协议 | `binary-formats.md` |
| 平台与外壳 | 平台接口、SSR、客户端导航 | `dom-shell-strategies.md` |
| 资产许可 | 计划用途与已知许可缺口 | `legal-and-deploy.md` |

可参考同类项目的规模与用时, 但不要从六个项目的工期变化推导通用承诺. 先验证影响可行性的最小完整功能链. 历史评级与工期保留在案例 §3.

## 4. 范围判定复核

依据 `scope-and-fingerprint.md` 确认内容能否快照、目标行为由什么驱动、客户端是否持有实现. React/Nuxt/Vue/R3F 等名称不直接决定可恢复性. 新证据影响原分类时更新对应能力的结论.

## 5. 开始实现前需要明确的信息

确认本次实现所需的架构入口、动画来源、bundle 结构、DOM 生成方式、关键版本、数据格式、资源缺失和验证状态. 只有依赖这些信息的步骤需要等待, 无需为无关条目完成完整调查.

已明确的范围和用途直接执行. 未要求部署时无需先做发布决策; 访问或使用条件按实际影响处理, 不把权利问题与技术完整性相互替代.

## 6. 常见误判

依赖存在不代表应用调用; vendor 字符串不是站点能力; 没有 `/api/` 不代表没有接口; 原文件不可见不代表序列化输出可恢复原源码. 反向例子与具体症状见案例 §6.

资源发现覆盖、版本识别与可观察状态分别核对. 核实一项不能自动确认其余项, 也不需要对未受新证据影响的结论重复调查.

## 7. 完成条件

当前实现所需的入口、数据与验证基准已经明确; 未确认项有具体影响范围. 记录相应参考文件和下一步可执行工作, 不以表格是否全部填写作为技术完成标准.
