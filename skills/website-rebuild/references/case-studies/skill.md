# Website Rebuild 入口案例

按需核对 SKILL.md 中方法的来源与覆盖范围. 项目数值描述各次记录, 不作为新项目的成功率或工期承诺.

## 使用前提与授权

objectarchive 在一类资产未采集的情况下, 五项检查持续通过四个里程碑. 用户要求补采后, 文件数从 1,591 增至 4,131, 原缺失约占补采后总数的 60%. 检查结论需要同时声明发现集合、采集范围与排除项; 该案例不提供额外采集许可[objectarchive].

## 适用范围

- C1: rauchg.com (Next 16/Turbopack) 从 Flight 输出重建服务端组件结构, 客户端组件按可获得的实现移植. 记录的 18/18 路由通过规范化语义比较和模块 ID 双射检查; 另一次盲逆向对照报告结构约 95%、行为约 98%. 后两项是项目评估值, 不代表全部运行状态等价.
- C2: 一个 R3F 站的 `useFrame` 回调使用 `MathUtils.damp(x, y, 7, t)`. 切片移植 18 个模块后, 记录为 CLEAN、8 个 canvas 和跨侧指标 99.5%. 渲染器由镜像提供; 结果覆盖该次输入和捕获状态.
- X: first-launch 的存档恢复采用策略 A 外壳, 9,856 个数值样本一致, 像素比较处于已记录容差内, 并通过自包含检查.
- X 的覆盖限制: 另一站 160 项目标资产中有 157 项在已搜索的存档年代未发现捕获, 虽然代码层覆盖完整, 离线运行仍为白屏. 需要分别评估代码、清单与媒体覆盖, 见 `archival-rescue.md` §1.9.

## Workflow / Flow - M1

先按打包形态选择分析单位. 一份 24,378 行的 webpack 产物可识别为 569 个模块, 但顶层声明扫描结果为 0; 对它应使用 `scripts/module-map.mjs` 的容器边界和依赖信息.

## Workflow / Flow - M(n+1)

一份通过既定检查的移植产物仍包含 14,271 行单文件代码, `e` 出现 2,962 次, 注释占 0.2%. 运行验收与可读性是不同目标.

该项目延迟绑定 6 个末尾单例后, 最大模块从 11,246 行缩小到 1,013 行. 两次分解失败最终定位为变换工具仍从原始 AST 生成 import 清单, 见 `readable-source.md` §3.1-3.1.3. 结构性限制与工具缺陷需要分别核实.

## Script Directory

F27 案例中, 含引号的正则字面量使手写词法扫描错位 16,177 行. 已支持语法应交给成熟词法器解析, 再在 token 流上匹配括号.

`module-map.mjs` 曾直接依赖 Babel, 与当时 `scripts/` 的依赖约定不符, 持续八个版本后才发现. 当前静态依赖检查用于报告可识别的导入, 其覆盖限制见脚本说明.
